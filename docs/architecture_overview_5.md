# Общая архитектура системы «Торнус Склад»

## 1. Обзор системы

«Торнус Склад» — система управления складом малого бизнеса. Система состоит из нескольких независимых компонентов, каждый из которых решает свою задачу и взаимодействует с остальными через чётко определённые интерфейсы.

**Компоненты системы:**

| Компонент | Технология | Назначение |
|-----------|-----------|-----------|
| База данных | PostgreSQL 16 | Хранение всех данных |
| REST API | FastAPI (Python) | Бизнес-логика, доступ к данным |
| Административная панель | Streamlit (Python) | Интерфейс для управления складом |
| Инструмент администрирования БД | pgAdmin 4 | Прямой доступ к PostgreSQL |
| Контейнеризация | Docker Compose | Изоляция и запуск всех сервисов |

## 3. Принцип многоуровневой архитектуры

Система построена по принципу **разделения ответственности**: каждый слой знает только о своём соседнем слое.

```
┌──────────────────────────────────────────────────────┐
│                   Streamlit Dashboard                 │  ← Слой представления
│  pages/*.py → api_client.py                          │    (UI + HTTP-клиент)
└─────────────────────┬────────────────────────────────┘
                      │ HTTP (JSON)
┌─────────────────────▼────────────────────────────────┐
│                   FastAPI Routers                     │  ← Слой API
│  routers/products.py, movements.py, analytics.py     │    (маршруты, валидация)
└─────────────────────┬────────────────────────────────┘
                      │ Python функции
┌─────────────────────▼────────────────────────────────┐
│                     CRUD Layer                        │  ← Слой бизнес-логики
│  crud.py                                             │    (операции с данными)
└─────────────────────┬────────────────────────────────┘
                      │ SQLAlchemy ORM
┌─────────────────────▼────────────────────────────────┐
│                   PostgreSQL Database                 │  ← Слой хранения
│  products, stock_movements                           │
└──────────────────────────────────────────────────────┘
```

**Следствие:** Streamlit не знает SQL. FastAPI не знает про HTML. CRUD не знает про HTTP. При замене любого слоя (например, Streamlit на React) остальные слои не меняются.

## 4. Поток данных — основные сценарии

### Сценарий 1: Просмотр остатков

```
1. Пользователь открывает страницу "Сводка" в браузере
2. Streamlit (1_Сводка.py) вызывает api.get_summary()
3. api_client.py отправляет GET http://api:8000/analytics/summary
4. FastAPI router вызывает crud.get_warehouse_summary(db)
5. CRUD выполняет SQL-запросы (COUNT, SUM) к PostgreSQL
6. Результат JSON проходит обратно по цепочке
7. Streamlit отображает метрики через st.metric()
```

### Сценарий 2: Регистрация прихода товара

```
1. Кладовщик заполняет форму на странице "Движения"
2. Streamlit вызывает api.create_movement({type: "IN", qty: 100, ...})
3. api_client.py отправляет POST http://api:8000/movements/
4. FastAPI валидирует данные через Pydantic схему MovementCreate
5. FastAPI вызывает crud.create_movement(db, data)
6. CRUD:
   a. Получает текущий остаток товара (qty_before = 50)
   b. Вычисляет новый остаток (qty_after = 50 + 100 = 150)
   c. Создаёт запись в stock_movements
   d. Обновляет products.current_stock = 150
   e. db.commit() — оба изменения атомарны
7. FastAPI возвращает 201 Created с данными движения
8. Streamlit показывает сообщение "Движение зарегистрировано"
```

### Сценарий 3: Импорт товаров из CSV

```
1. Пользователь загружает CSV на странице "Импорт"
2. Streamlit читает файл как bytes, отправляет через _post_file()
3. api_client.py отправляет POST /products/import/csv (multipart/form-data)
4. FastAPI читает файл, парсит CSV через csv.DictReader
5. Для каждой строки — вызов crud.bulk_import_products()
6. CRUD проверяет каждый SKU на дубликат (SELECT по индексу)
7. Создаёт новые товары или обновляет/пропускает существующие
8. Возвращает статистику: {created: 35, updated: 0, skipped: 2, errors: [...]}
9. Streamlit отображает итоги и предлагает скачать штрих-коды
```

## 5. Инфраструктура Docker Compose

```yaml
# Порядок запуска:
db          → запускается первым, проходит healthcheck (pg_isready)
api         → ждёт db: condition: service_healthy
dashboard   → ждёт api (просто depends_on, без healthcheck)
pgadmin     → ждёт db (независимо от api)
```

**Сетевое взаимодействие:**

Сервисы общаются по именам (`db`, `api`), а не IP. Docker Compose создаёт внутреннюю DNS-зону. Снаружи (с хост-машины) доступны только проброшенные порты:

| Снаружи | Внутри Docker | Сервис |
|---------|--------------|--------|
| `localhost:5432` | `db:5432` | PostgreSQL |
| `localhost:8000` | `api:8000` | FastAPI |
| `localhost:8501` | `dashboard:8501` | Streamlit |
| `localhost:5050` | `pgadmin:80` | pgAdmin |

**Хранилище данных** — Docker Volume `postgres_data` — монтируется в контейнер PostgreSQL. При пересоздании контейнера данные сохраняются. При `docker volume rm pro_sklad_postgres_data` — уничтожаются.

## 6. Безопасность и аутентификация

В текущей версии реализована минимальная защита, соответствующая учебному проекту:

```
┌─────────────────────────────────────────────────────┐
│ Уровень доступа                                      │
├─────────────────────────────────────────────────────┤
│ Streamlit Dashboard → пароль (env DASHBOARD_PASSWORD)│
│   Проверка через st.session_state в каждой странице  │
├─────────────────────────────────────────────────────┤
│ FastAPI → открытый (без авторизации)                 │
│   Доступен всем в Docker-сети                        │
├─────────────────────────────────────────────────────┤
│ pgAdmin → логин/пароль (env PGADMIN_DEFAULT_*)       │
│   Прямой доступ к БД для администратора              │
└─────────────────────────────────────────────────────┘
```

**Для production** потребуется: JWT-авторизация на FastAPI, HTTPS (nginx/Traefik как reverse proxy), ограничение CORS.

## 7. Модуль генерации штрих-кодов

Генерация PDF — полностью клиентский (dashboard-side) процесс. API не задействован:

```
┌─────────────────────────────────────────────────────┐
│ dashboard/barcode_utils.py                           │
├─────────────────────────────────────────────────────┤
│                                                     │
│  input: list[{sku: str}]                            │
│          │                                          │
│          ▼                                          │
│  python-barcode → Code128 PNG (в памяти, BytesIO)   │
│          │                                          │
│          ▼                                          │
│  ReportLab Canvas → сетка 5×6 на листе A4           │
│          │                                          │
│          ▼                                          │
│  output: bytes (PDF в памяти, не на диске)          │
│                                                     │
│  Streamlit: st.download_button(data=pdf_bytes)      │
└─────────────────────────────────────────────────────┘
```

Вся генерация происходит в памяти (через `BytesIO`) — временные файлы на диск не пишутся. Это важно для контейнерной среды с read-only файловой системой.

## 8. Расширяемость — как добавить мобильное приложение

FastAPI изначально проектировался с прицелом на будущее мобильное приложение для складских работников (Kotlin/Android).

**Что уже готово:**
- Полная Swagger-документация на `/docs` — разработчики мобильного приложения видят все эндпоинты, параметры и форматы ответов
- REST API без состояния (stateless) — любой клиент может делать запросы
- CORS настроен как `allow_origins=["*"]` — принимаются запросы с любого источника

**Что нужно добавить для мобильного клиента:**

```
Текущая архитектура:
Streamlit → FastAPI → PostgreSQL

Расширенная архитектура:
Streamlit    ─┐
Kotlin App   ─┼─► FastAPI → PostgreSQL
Web App (?)  ─┘
```

Для защиты мобильного API потребуется добавить JWT-аутентификацию:
```python
# В FastAPI — добавить зависимость
from fastapi.security import HTTPBearer
security = HTTPBearer()

@router.post("/movements/")
def create_movement(data: MovementCreate,
                    token: str = Depends(security),  # ← новая строка
                    db: Session = Depends(get_db)):
    ...
```

Мобильное приложение будет работать с теми же эндпоинтами, что и Streamlit, так как весь интерфейс с данными уже реализован.

## 10. Итог

Архитектура «Торнус Склада» следует принципу **разделения ответственности**: хранение данных, бизнес-логика и представление изолированы друг от друга и взаимодействуют через стандартные интерфейсы (HTTP REST и SQL). Это обеспечивает:

- **Независимость компонентов:** можно заменить Streamlit на React или добавить мобильное приложение Kotlin, не меняя API и базу данных.
- **Изоляция через Docker:** каждый сервис работает в своём контейнере со своими зависимостями, без конфликтов версий библиотек.
- **Единый источник правды:** все данные хранятся в PostgreSQL; и Streamlit, и будущее мобильное приложение читают одни и те же данные через API.
- **Прозрачность для разработчика:** FastAPI автоматически генерирует документацию, что снижает порог входа для новых участников команды.
